# 5. Connection state machine and the request path

These are the units involved:

- `bearings.http1.io` (`TH1Io`: the read buffer, the write buffer and the flush)
- `bearings.http1.conn` (`TH1Conn` and `TConnState`: the HTTP/1.1 state machine of one connection)
- `bearings.http1.dispatch` (`TH1Dispatcher`: the loop task that drives the state machine and moves requests between it and the service).
- `bearings.http1.config` holds the options (`TH1Config`), the two presets (`ConformanceH1Config`, `ProductionH1Config`), their validation and `ApplyH1Config`.

## 5.1 Reading a request head

`TH1Dispatcher.PollReadHead` takes an exchange from the loop's pool before anything is parsed, because the head is parsed into the exchange's header list. `TH1Io.Parse` calls `ServerParseHeaders` (`bearings.http1.role`) on the unread bytes; the parser (`bearings.http1.parser`) checks the syntax byte by byte against the RFC 9110 and 9112 grammars, and `bearings.http1.role` applies the HTTP rules. Nothing is copied: the header list gets external entries whose offsets are relative to the head, the target is split into slices by `bearings.http.uri`, and the head leaves the read buffer as a pinned view (`TReadBuf.SplitTo`). A head that arrives in pieces is parsed again only when the new bytes hold an end of head (`IsCompleteFast` scans from 3 bytes before the previous length), so a slow client costs no repeated full parse.

Each read asks the socket for `TReadStrategy.Next` bytes: 8 KiB at first, doubled after a read that filled it, halved after two reads in a row that used less than half, and never more than `max_buf_size - Len`, so the read buffer never holds more than `max_buf_size` (`DEFAULT_MAX_BUFFER_SIZE`, 417 792 bytes; minimum 8192). Limits with their automatic responses: a request-target over `MAX_URI_LEN` (65 534 bytes) gives 414; more than `MaxHeaders` fields (100 by default), a head over `MaxHeaderSize`, a head that reaches `max_buf_size`, or a header name of 64 KiB or more gives 431; any other syntax error gives 400 (`ServerErrorStatus`).

**Framing and smuggling.** `bearings.http1.role` decides the body length (RFC 9112 section 6.3): `Transfer-Encoding: chunked` wins over `Content-Length`; when both are present the `Content-Length` lines are dropped from the list and the connection closes after the response; a `Transfer-Encoding` whose last coding is not `chunked`, a `Transfer-Encoding` in an HTTP/1.0 request, an invalid `Content-Length`, or several `Content-Length` values that differ are rejected with 400. The lenient options of `TParserConfig` are all off by default. The body decoder (`TDecoder`, `bearings.http1.decode`) is a resumable state machine that returns slices of the read buffer and closes reading on any malformed chunk-size line, missing CRLF, overflowing size or oversized extension (the handler sees a body error and may still answer; the connection is not reused and ends with outcome `io`, 5.7); trailers are copied into a per-connection scratch buffer and parsed into the exchange's `ReqTrailers` list under the same header limits.

**The PROXY protocol header** (`TH1Config.ProxyProtocol`, `bearings.rt.proxyproto`). When a proxy stands in front, every connection starts with one header, v1 (a text line of at most 107 bytes) or v2 (a signature, a command, a family and an address block, TLVs skipped), before the first request. `TH1Conn.PollReadHead` reads it before the first head parse, under the same header read timer, through `PollReadProxy`: the parser is a pure function over the read buffer that says ok (consume the bytes), need more (read on; at most `PROXY_MAX`, 4 KiB) or error. The address it carries replaces the connection's peer (`TH1Dispatcher.Peer` and the request head's `Peer`, so `TExchange.PeerAddr` and the access log see it; the observer's `OnAccept` saw the socket's). A missing or invalid header ends the connection with the parse error `h1peProxyProtocol` and no response, since the sender is not an HTTP client; EOF before any byte (a proxy's connect check) is a normal end. v1 `UNKNOWN`, v2 `LOCAL` and v2 without an IP address keep the socket's peer.

## 5.2 States and keep-alive

`TConnState` keeps the reading and the writing side apart: `Reading` is `rdInit` (waiting for or parsing a head), `rdContinue` (head read with `Expect: 100-continue`, body not asked for yet), `rdBody`, `rdKeepAlive` (request complete; wait for the response) or `rdClosed`; `Writing` is `wrInit`, `wrBody`, `wrKeepAlive` or `wrClosed`. `KeepAlive` (`TKA`) is `kaBusy` during a request, `kaIdle` between requests and `kaDisabled` once the connection must close after the current response. When both sides reach their keep-alive state, `TryKeepAlive` resets both to `Init` or, if keep-alive is disabled, closes both. The dispatcher disables keep-alive on its own at the request that reaches `MaxRequests`, and at the first request read after `MaxConnectionMs` has passed since the connection was set up (the loop clock): that response says `Connection: close`. There is no timer for the age, so an idle connection past it stays until its next request or the header read timeout; a request in progress is never cut (nginx's `keepalive_requests` and `keepalive_time`). `Idle` sets `NotifyRead` when a header read timeout is configured, so the dispatcher loops once more and re-arms the timer right after the response; the header read timeout therefore also bounds an idle keep-alive connection. After a response, `MaybeNotify` tries one read when the buffer is empty and sets `NotifyRead` when bytes are buffered, so a pipelined request is parsed without waiting for another readiness event.

HTTP/1.1 keeps the connection open unless either side sent `Connection: close`; HTTP/1.0 closes unless the client sent `Connection: keep-alive`. `EnforceVersion` answers a 1.0 client with a 1.0 response and adds `connection: close` to a 1.1 response when the server will close (`FixKeepAlive` for 1.0). A response body of unknown length to a 1.0 client can only end by closing the connection.

**One request at a time.** The next head is parsed only when no service call is in flight (`InFlight = nil`) and the state is back to `rdInit`. Pipelined requests wait unparsed in the read buffer, and responses leave in request order without any reordering structure, because nothing on the wire says which request a response answers. A slow handler delays the later requests of its own connection, not those of other connections.

## 5.3 The service call

`PollReadHead` opens the exchange's body channel and prepares an upgrade slot when the request asks for one (5.8); `RecvMsg` fills the exchange's head, then calls `THttpService.Call(Ex)`, which returns a `TServiceCall` and must not answer or read the body (builds with assertions check it). The handler's code runs only in `TServiceCall.Poll`, which `PollMsg` calls from `PollWrite` every time the connection runs while the call is in flight, until it returns `cpReady` after exactly one terminal call. Two steps instead of one because the same `PollLoop` iteration runs the rest of `PollRead` between them: it fetches the first body chunk into the channel before the handler's first poll (so a handler that reads finds data), and it may detect the client's EOF, in which case the call is dropped (`Drop(Ex, False)`) without ever being polled. A stateless call object returned for every request costs one virtual call and no allocation.

## 5.4 Writing

A response head is encoded by `ServerEncode` straight into the write cursor (`TWriteBuf.Headers`, a `TCursor` over a pooled `TByteVec`) when nothing is queued. The encoder chooses the framing and returns a `TEncoder` (`bearings.http1.encode`): `Content-Length` when the length is known, `Transfer-Encoding: chunked` when it is not (HTTP/1.1), close-delimited for a 1.0 client; it adds `Date` and a zero `Content-Length` when needed, removes framing headers from responses that must not have a body (HEAD, 1xx, 204, 304, a 2xx to CONNECT), groups header lines of one name at the position of the first, joins `Connection`, `Transfer-Encoding` and `Trailer` lines, and writes names in lowercase unless `TitleCaseHeaders`. A 1xx status other than 101 cannot be sent on this path: a 500 head is written instead and the connection ends with a user error. An HTTP/0.9 or HTTP/3.0 response version raises `EH1Panic` before the encoder runs; the loop aborts the connection task (no response, no completion event).

Body pieces go through `TWriteBuf.Buffer`: an entry of at most `MAX_COPY_SIZE` (4 KiB) is copied into the cursor and its data released at once; a larger entry, a file range, and every entry that arrives while something is queued goes into the queue (`TBufList`, a ring of `QUEUE_SLOTS` = 32 entries in a pooled block). The cursor is always written before the queue, so copying a later piece would send it before the queued bytes; that is why "everything behind a queued entry is queued", and why a head that must be written while entries are queued (the automatic 400/414/431 of a parse error, the automatic `100 Continue`) is queued behind them as a `qkBytes` entry (`BufferAfterQueue`) instead of being written into the cursor between an earlier response's head and body.

`PollFlush` writes the cursor with `write(2)` when nothing is queued, else the cursor and the queued memory entries with one `writev(2)` (at most `MAX_WRITEV_BUFS` = 64 slices), and a file entry at the front with `sendfile(2)` (at most `SENDFILE_MAX_CHUNK` per call). The bytes on the wire for a file body equal those of a memory body with the file's content; a file frame in a chunked body gets the chunk framing around the file range (`BufferFileFrame`). A write that returns 0 with bytes left is reported as `IO_ERRNO_WRITE_ZERO`. `CanBuffer` bounds the memory one response can hold: the dispatcher polls the body source only while the write buffer holds less than `max_buf_size` and fewer than 16 entries are queued. With `PipelineFlush` on only the 16-entry bound applies: the cursor is not bounded, because the responses of a pipelined batch collect there.

**Pipeline flush** (`TH1Config.PipelineFlush`, on in the production preset): while the read buffer still holds bytes of further requests and nothing is queued, `PollFlush` writes nothing, so the responses to a pipelined batch leave in one write (measured 4x the pipelined throughput). A queued entry is written even then, because while it is queued no later head can be buffered and nothing would wake the task. Once the connection is done, `PollInner` flushes what pipeline flush held (`HoldsPipelinedWrite`, `PollFlushHeld`) before an upgrade hand-off, the parts hand-off or the shutdown; without it a 101 response followed by client bytes would be lost (section 10).

## 5.5 Expect, half-close, draining

**`Expect: 100-continue`.** A head with the field, a non-empty body and a version above 1.0 sets `rdContinue`, and the body channel starts without a request for data. The connection writes `HTTP/1.1 100 Continue` only when the handler first reads the body and no response head was written yet (`PollReadBody` in `rdContinue`), then switches to `rdBody`. A handler that answers without reading never asks for it, and the client is spared the upload; a body left unread then goes through draining without a 100.

**Half-close.** With `HalfClose` off (the default) a connection in the middle of a request keeps one read pending while the response is in progress (`MidMessageDetectEof`, skipped while the read buffer holds a pipelined request): EOF there closes the read side and ends the connection with `incomplete` (no response, no shutdown; the call in flight is dropped). With `HalfClose` on, the response is finished first.

**Draining.** When the application finished without reading the whole body, `PollDrainOrCloseRead` reads once and discards what arrives; if the body has not ended by then, reading is closed and the connection is not reused. A framing or socket error found while draining ends the connection with outcome `io` (5.7).

## 5.6 Errors and automatic responses

`OnParseError` runs when a head cannot be parsed. If the read buffer starts with the HTTP/2 connection preface (`H2_PREFACE`, all 24 bytes), nothing is written and the outcome is `parse_version_h2`. Otherwise, if no response was started, a bodyless head with the status of `ServerErrorStatus` (400, 414 or 431) is written with `connection: close`, `content-length: 0` and `date`, the error is stored, and the dispatcher flushes, shuts the socket down and then reports the stored error (`TakeError` runs after `PollShutdown`). Errors are `THyperError` values (`bearings.http.error`), a plain record whose `Kind` says what failed and whose `Cause` adds an errno, a decoder error, a fixed text or the connection's cold error text; copying one is a memory copy and a routine with such a local gets no exception frame. `OutcomeOf` maps the final result to a `TConnOutcome` in the order of `conformance/SPEC.md` 7.2 (`ok`, `timeout`, `parse_too_large`, `parse_version_h2`, `parse`, `incomplete`, `user`, ..., `io`, `other`); the response body ending before its declared length counts as a user error.

## 5.7 Timeouts

The **header read timeout** (`HeaderReadTimer`; `tsDefault` is 30 s when the connection has a timer, none without) limits the time from the start of a head read to a complete head. It is armed lazily before `Parse` and cancelled lazily when a head is parsed; on expiry the head read fails with `hekHeaderTimeout` and nothing is written. Because `Idle` re-arms it, it is also the idle keep-alive timeout.

The **body rate rule** (`BodyReadTimeoutMs`, `BodyMinRate`; 30 s and 1 KiB/s in the production preset, off in the conformance preset) measures only the time the server waits for request body bytes: a wait starts when `PollReadBody` finds no byte, which happens only while the handler's channel has room, and ends with the next frame. The body fails with `NewBodyIo(ETIMEDOUT)` when one wait lasts `BodyReadTimeoutMs`, or when the waits since the first byte add up to T >= `BodyReadTimeoutMs` and fewer than `BodyMinRate` x T / 1000 bytes came (the wait before the first byte counts only for the first rule). Reading closes, the handler sees a body error (`BodyErrorIsTimeout`) and answers, and the connection closes after that response. Every request body error (this rule, malformed framing, a socket error, whether the handler reads the body or the server drains it) is kept by the connection too and reported after the response and the shutdown (`TakeError`), so the outcome is `io` (hyper ends such a connection `ok`; section 10). Both timeouts need `TH1Config.Timer`; `ValidateH1Config` refuses a timeout without one.

## 5.8 Upgrades and CONNECT

A request with an `Upgrade` header (HTTP/1.1) or the CONNECT method sets `wantUpgrade`; `PrepareUpgrade` creates a reference-counted `TUpgradeSlot` (one reference for the connection side, one for the exchange; an older slot still pending is cancelled) and links it to the exchange. A 101 response, or a 2xx to CONNECT, makes the encoder mark the response as the connection's last (`IsLast`), so writing ends in `wrClosed`, `TryKeepAlive` closes the read side, and `PollInner` sees the pending slot and ends with `dsUpgrade` without a shutdown. `Finish` then acts by `TH1ConnMode`: `cmWithUpgrades` takes the transport and the unread bytes out of `TH1Io` (`IntoInner`: the bytes stay in their pinned block, no copy), builds a `TUpgraded` (`bearings.rt.stream`) that takes over the socket's readiness source, tracks it in the loop's `Upgraded` list (`U.Track`, so that a stop reaches it, 5.9), gives it a `CloseProc` that calls `TConnHooks.UpgradedClosed` when the server has hooks, and fulfils the slot; a `TUpgradeDelivery` task queued after the observer's `OnConnClose` calls the handler, so the close is reported before the upgraded connection starts. `cmPlain` and `cmWithoutShutdown` do not hand upgrades over: the handler gets `upgrade expected but low level API in use`; `cmPlain` then closes the socket, and `cmWithoutShutdown` hands the transport and the unread bytes to the observer as `TConnParts` whenever the connection ends without error. A slot whose response was not an upgrade stays with the connection: a later upgrade request replaces it (the older handler gets `upgrade expected but not completed`), and a connection that finishes while it is set ends through the upgrade path.

## 5.9 The end of a connection

`PollInner`: after `PollLoop`, once `IsDone` holds, flush what pipeline flush held, then either prepare the upgrade or, when the mode asks for it, `PollShutdown` (flush, then `shutdown(SHUT_WR)`, so the client reads the whole last response followed by EOF) before `TakeError`; an error propagated from `PollLoop` skips flush and shutdown. `PollCatch` turns an error into the body channel's `connection error` for a handler still reading. `Finish` then: the hand-off (5.8); `DropAll` in a fixed order (close the transport if still owned, cancel the upgrade slot still held by the connection state, cancel the exchange and drop the call in flight with `Completed = False`, close the body sender with the incomplete-message error, release the response body source, cancel and release a pending upgrade not handed on, release the exchange, `TH1Conn.Done`, unlink from the loop's list, `TConnHooks.ConnDone`); the outcome to `TConnObserver.OnConnClose`; the hand-off actions; `Close`. `Abort` (an exception, the stop deadline) runs `DropAll` only, with no completion event.

**Graceful shutdown of one connection** (`GracefulShutdown`): nothing after the hand-off; else keep-alive is disabled, a connection with nothing read or written (or writing already closed) is closed at once, and the task is woken so that an idle connection notices now. What a client sees during `TServer.Stop`: a request the server has read gets its full response with `connection: close`; a connection on which no request byte was read when the stop reached its loop (idle keep-alive, just accepted, a request still in the socket buffer) is closed without a response; a connection that enters the accept queue between the last `accept4` and the close is reset by the kernel. An upgraded connection no longer belongs to a dispatcher: the stop calls `TUpgraded.Shutdown`, which asks its listener to end its protocol (the default closes the socket; a WebSocket sends close 1001 `server shutdown` and runs the close handshake), and the deadline aborts it (the listener's `Aborted`, then close).

## 5.10 Wake sources

A task may return "pending" only when something will run it again: a socket read or write that returned `EAGAIN` in this run (the next readiness event), a timer, a service call or body source that returned pending (they must call `Ex.Wake`), a body channel waiting for its receiver (the receiver's next read wakes the sender), or the task's own wake (yield, the channel's wake). Builds with `-dWD_DEBUG` check this at the end of every run that returns pending (`AssertWakeArmed`, counted in `WakeAssertFailures`). Builds with `-dWD_DEBUG -dWD_STALL` add the stall detector (`WD_STALL` alone does not compile): each loop scans its connections once per second and reports, once, a connection that is mid-message, has not run for `STALL_MS` (60 s) and waits on the server rather than on the client (`TH1Dispatcher.StallCandidate`); a connection whose last run waited on a read or write `EAGAIN` with nothing owed is not reported.

**Server hooks.** `TConnHooks` (`RequestStarted`, `RequestDone`, `ConnDone`, `UpgradedClosed`) is how the server layer attaches the connection limit, the metrics and the access log; it is nil when none is on, and the dispatcher then tests one pointer per event.
